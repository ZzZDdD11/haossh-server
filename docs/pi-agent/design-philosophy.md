## 一、从最根本的问题出发：什么是 Agent？

抛开所有框架，agent 的本质是一个**循环**：

```
感知（输入） → 推理（LLM） → 行动（工具调用） → 观察结果 → 感知（回到输入）
```

这就是所谓的 **agent loop**。无论你用 LangChain、AutoGPT 还是 Pi，这个循环都不会变。它是 agent 的"第一性原理"——所有东西都是在这个循环之上做的工程决策。

那么问题来了：既然循环这么简单，为什么 agent 框架会这么复杂？

答案在于：**循环之外有大量不可避免的工程现实**：

1. LLM 不是一家，每家 API 都不同（OpenAI、Anthropic、Google...）
2. 工具调用的格式、流式输出、重试、错误处理各不相同
3. 上下文会爆掉，需要压缩、分支、摘要
4. 用户要和这个循环交互（终端 UI、会话管理）
5. agent 会执行危险操作（读写文件、跑命令、发网络请求）
6. 这一切要可扩展、可测试、可维护

**Pi 的设计哲学，就是把"不变的循环"和"会变的工程现实"严格分离开。** 这是理解 Pi 整个架构的钥匙。

## 二、架构分层：每一层只解决一个根本问题

Pi 把整个系统拆成四个包，这不是随便分的，而是**按第一性问题正交分解**：

```
┌─────────────────────────────────────────────┐
│  pi-coding-agent   ← 用户如何与 agent 交互？  │  上层
├─────────────────────────────────────────────┤
│  pi-agent-core     ← agent 循环怎么跑？      │  中层
├─────────────────────────────────────────────┤
│  pi-ai             ← 怎么和 LLM 说话？       │  底层
├─────────────────────────────────────────────┤
│  pi-tui            ← 怎么在终端画界面？       │  正交辅助
└─────────────────────────────────────────────┘
```

### 第一性分解的逻辑

| 包 | 解决的根本问题 | 为什么单独成层 |
|---|---|---|
| `pi-ai` | LLM 供应商碎片化 | 屏蔽 OpenAI/Anthropic/Google 的 API 差异，上层只面对统一接口 |
| `pi-agent-core` | agent 循环的工程化 | 工具调用、状态管理、上下文管理——循环的"骨架肌肉" |
| `pi-coding-agent` | 编码这个具体场景 | 把通用 agent 落地到"写代码"这件事上 |
| `pi-tui` | 终端渲染 | 和 agent 逻辑正交，只管把字符画到屏幕上 |

### 包一览

| 包名 | 描述 |
|------|------|
| `@earendil-works/pi-ai` | 统一多供应商 LLM API（OpenAI、Anthropic、Google 等） |
| `@earendil-works/pi-agent-core` | 具备工具调用和状态管理的 Agent 运行时 |
| `@earendil-works/pi-coding-agent` | 交互式编码 Agent CLI |
| `@earendil-works/pi-tui` | 带差分渲染的终端 UI 库 |

### 关键洞察

`pi-tui` 和 `pi-ai` 是正交的——一个管输出（给用户看），一个管输入（给 LLM 用），它们都不"知道" agent 是什么。而 `pi-agent-core` 是那个把一切串起来的循环核心。

这种分层的好处：**换 LLM 不影响 agent 逻辑，换 UI 不影响 agent 逻辑，换应用场景（coding → 聊天）也不影响 agent 核心。** 这就是正交分离带来的可替换性。

### Agent 交互架构推断

虽然 README 本身不展开 agent loop 的实现，但从功能模块可以推断其设计：

- **会话管理**：支持会话管理、分支和树状导航
- **上下文压缩**：具备上下文压缩和分支摘要功能，应对长上下文下的 Token 消耗与注意力保持
- **多模式输入输出**：
  - **RPC 模式**：通过 stdin/stdout JSONL 进行集成
  - **JSON 事件流模式**：打印带有结构化事件的输出
- **底层定制能力**：支持自定义模型和自定义 provider，甚至可以实现自定义 API 和 OAuth 流程

## 三、"核心极小"原则：为什么拒绝把功能塞进核心？

这是 Pi 最鲜明的设计立场，在 `CONTRIBUTING.md` 里白纸黑字写明：

> **pi 的核心是极简的。不属于核心的功能应作为扩展实现。**
> **会导致核心膨胀的 PR 大概率会被拒绝。**

### 第一性推导

问一个根本问题：**框架的核心应该包含什么？**

朴素直觉是"把常用功能都内置"。但 Pi 的回答相反——**核心应该只包含"无法被扩展机制实现的东西"**。

为什么？因为：

1. **核心代码是全局风险**：核心的一个 bug 影响所有用户。扩展的 bug 只影响用这个扩展的人。
2. **核心是维护负担**：核心每多一个功能，就多一份要永久维护、测试、不能破坏的代码。
3. **核心是认知负担**：新贡献者要理解整个框架，核心越大门槛越高。

所以 Pi 的扩展机制（TypeScript 扩展、技能 Skills、提示模板、主题、包）本质上是在回答一个问题：**"核心要暴露多少钩子，才能让外部实现一切？而且这些钩子本身也不能臃肿。"**

`CONTRIBUTING.md` 里有一句话点透了这种克制：

> **即便是扩展钩子点也需要深思熟虑地讨论，避免引入难以维护的臃肿和复杂交互。**

这不是"能扩展就行"，而是"连扩展点本身都要最小化"。

### 核心扩展能力一览

Pi 的核心能力通过以下几种方式延展：

- **TypeScript 扩展**：用于添加工具、命令、事件和自定义 UI
- **技能（Skills）**：实现可重用的、按需调用的智能体能力
- **提示模板**：可通过斜杠命令展开的可重用提示词
- **主题与包**：支持终端主题定制，以及通过 Pi packages 打包和分享扩展、技能、提示词与主题

## 四、安全边界的第一性思考：不内置权限系统

这可能是最反直觉的设计决策：**Pi 默认不限制文件系统、进程、网络、凭证访问。**

### 为什么"不限制"反而是正确选择？

从第一性思考"安全边界应该在哪"：

1. **如果 agent 框架自己实现权限系统**——它要重新实现文件系统沙箱、进程隔离、网络过滤、凭证管理。这每一个都是极其困难的安全工程问题。一个 agent 框架不可能比 Docker、比操作系统内核、比 OpenShell 做得更好。
2. **权限系统的 bug = 安全漏洞**：如果框架说"我限制了"，但实现有 bug，用户会信任这个限制而放松警惕，反而更危险。
3. **操作系统已经提供权限边界**：用户权限、容器、虚拟机、沙箱——这些是成熟的、经过验证的隔离机制。

所以 Pi 的哲学是：**诚实地说"我不做权限"，然后把安全责任交给真正擅长的东西**——容器和沙箱。

### 三种容器化模式

```
Plain Docker（最简单，密钥进容器）
    ↓ 隔离增强
Gondolin（微虚拟机，认证留宿主机，仅隔离内置工具）
    ↓ 隔离增强
OpenShell（五维策略控制：文件/进程/网络/凭证/推理，密钥不进沙箱）
```

| 模式 | 隔离范围 | 适用场景 | 注意事项 |
|---|---|---|---|
| **Gondolin 扩展** | 内置工具和 `!` 命令 | 本地微虚拟机隔离，认证保留在宿主机 | `pi` 在宿主机运行，工具路由进 VM；覆盖 `read/write/edit/bash/grep/find/ls` |
| **Plain Docker** | 整个 `pi` 进程在本地容器中 | 简单的本地隔离 | Provider API 密钥会进入容器；切勿挂载宿主机 `~/.pi/agent` |
| **OpenShell** | 整个 `pi` 进程在策略控制沙箱中 | 本地或远程托管沙箱 | 需 OpenShell 网关；推理路由可使原始 API 密钥不进入沙箱 |

### 第一性洞察

安全不是"在应用层加锁"，而是"在正确的层做隔离"。Pi 把安全边界放在容器/OS 层，而不是自己重新发明。这和 Unix 哲学一致——**做一件事并做好，安全隔离交给专门的安全层。**

### 关键设计约束

扩展（Extensions）运行在 `pi` 进程所在的位置。若采用宿主机 `pi` + 工具路由扩展的模式，其他自定义扩展工具 **仍将在宿主机上运行**，除非它们也委托其操作到隔离环境。

## 五、"你必须理解你的代码"——关于人与 AI 协作的第一性原则

`CONTRIBUTING.md` 里有唯一一条被加粗强调的规则：

> **The One Rule: 你必须理解你的代码。**
> 如果无法解释你的改动做了什么、如何与系统其余部分交互，PR 将被关闭。

### 为什么这条是"唯一规则"？

因为从第一性看：**代码库的长期价值不取决于代码写了什么，而取决于有没有人能维护它。**

- AI 生成的"看起来能跑"的代码，如果不被理解，就是技术债务的核弹。
- 自动关闭新贡献者 PR、对批量 AI issue 永久封禁——这些看起来"不友好"的政策，本质都是在保护一件事：**确保每一行进入核心的代码，都有一个人能为之负责。**

这条规则之所以是"唯一"，是因为**如果你满足了它，其他规则（测试、lint、格式）都是机械的、可自动化的；但如果你不满足它，其他规则再严格也没用。**

### 贡献门控机制

这是该项目最独特的治理设计：

| 状态 | 含义 | 权限 |
|---|---|---|
| 默认 | 新贡献者的 issue 和 PR | **自动关闭** |
| `lgtmi` | 维护者回复此标记 | 未来 issue 不再自动关闭（**不**包含 PR 权限） |
| `lgtm` | 维护者回复此标记 | 未来 issue 和 PR 均不再自动关闭 |

- 维护者每日审阅自动关闭的 issue，重新打开有价值的。
- 周五至周日提交的 issue 不保证被审阅，紧急问题需到 Discord 提出。
- 未获得 `lgtm` 批准前，不要提交 PR。

### 治理设计背后的逻辑（FAQ 要点）

1. **为何自动关闭新 issue/PR？** — 收到的 issue 数量超出维护者实时审阅能力，自动关闭创造缓冲区，让维护者按自己的节奏审阅。
2. **为何周末优先级低？** — 工作时间内分类处理，周末积压的 issue 在周一队列中可能被降低优先级或遗漏。
3. **为何部分 issue 无回复？** — 回复本身也是维护工作，低质量/重复/不符合指南的 issue 会被直接关闭不讨论。
4. **为何不让 AI 做分类？** — AI 可辅助但不可做最终决策，打磨过的 AI 生成 issue 仍可能错误或误导。
5. **这是否对贡献者不友好？** — 不是。这是防止倦怠和垃圾信息的护栏，短小、具体、可复现的 issue 和深思熟虑的贡献是欢迎的。

### 封禁政策

- 忽略 `CONTRIBUTING.md` 两次 → GitHub 账号永久封禁
- 用 agent 批量生成 issue → 永久封禁
- 通过自动化大量提交 issue → 永久封禁，不可撤销

## 六、复杂性管理：RFC 0031 教你什么叫"把复杂性拒之门外"

[RFC 0031 · Terminal Multiplexers](https://rfc.earendil.com/0031/)（作者：Armin Ronacher）是一篇教科书级的"复杂性管理"文档。它讲的是 pi 在 tmux/screen 下遇到的键盘、粘贴、图像、超链接等数十种边界问题。

但真正值得学的是它的**设计态度**：

> **当多路复用器支持不可靠时，Pi 倾向于禁用功能，而不是实现脆弱的部分支持。**

这是反直觉的——很多框架的默认反应是"加 workaround 让它尽量工作"。Pi 的反应是"如果不能可靠工作，就关掉它"。

### 第一性推导

问：**部分支持 vs 不支持，哪个更好？**

- 部分支持：用户以为功能可用，结果在边界情况下静默失败 → 不可预测 → 信任崩塌
- 不支持：用户明确知道不可用 → 可预测 → 可以找替代方案

**可预测性 > 功能完整性。** 这就是为什么 Pi 在 tmux 下默认禁用图像和超链接——宁可少一个功能，也不要一个"有时工作有时不工作"的功能。

### 反复出现的挑战

Pi 在多路复用器下需要面对的复杂性类别（每类都对应"功能 vs 可靠性"的权衡）：

1. **键盘输入**：修饰符丢失、Shift+Enter 与 Ctrl+J 不可区分
2. **粘贴**：括号粘贴标记可能被重写为 CSI-u 序列
3. **能力协商**：环境变量不可靠，多路复用器应自己回答或代理查询
4. **转义序列透传**：原始透传危险，需要特性感知和面板感知
5. **图像与图形**：直接图像放置的坐标/ID 对面板无意义
6. **超链接**：OSC 8 可能被 tmux/screen 静默吞没
7. **颜色与主题检测**：真彩色可能被错误解析，动态主题变化未解决
8. **焦点/鼠标/分离/死亡面板**：生命周期行为应面板本地化且可靠
9. **回滚与重绘**：终端不暴露可移植的 API 来查询或恢复回滚位置
10. **可调试性**：协议状态应可检查

### Pi 的实际选择

| 场景 | Pi 的决定 | 理由 |
|---|---|---|
| tmux 下 Kitty 图像 | 默认禁用 | 透传脆弱 |
| tmux/screen 下 OSC 8 超链接 | 默认禁用 | 可能被静默吞没，URL 消失比没有更糟 |
| 键盘协议 | 不实现 Kitty 渐进增强协商 | 实现会很混乱，不值得 |
| 死亡 tty 写入 | 显式 SIGHUP/SIGTERM + "死亡终端"紧急退出 | 不让 agent 在已删除的 tty 上旋转 |

### 核心设计理念

Pi 试图**将复杂性拒之门外**，保持核心功能可测试和可管理。务实而非贪婪：不是试图迎合每种情况，而是在功能支持和复杂性管理之间取得平衡。

## 七、总结：Pi 的四条第一性原则

把以上分析提炼，Pi 的设计哲学可以归结为四条第一性原则：

| 第一性原则 | 具体体现 |
|---|---|
| **正交分离** | 四个包各管一件正交的事，循环核心与 LLM/UI/场景解耦 |
| **核心极小** | 核心只放无法被扩展实现的东西；扩展机制本身也要最小化 |
| **安全交给正确的层** | 不自造权限系统，用容器/沙箱做隔离；诚实声明能力边界 |
| **可预测性优于功能** | 不可靠的功能宁可禁用；不理解代码的 PR 一律拒绝 |

### 一句话概括

> 不要在核心里解决可以用更合适的工具在更合适的层解决的问题——无论它是 LLM 供应商差异、安全隔离、还是终端渲染。核心只做一件事：把 agent 循环跑对，然后把其他一切交给扩展和外部边界。

## 附：供应链安全加固要点

Pi 将 npm 依赖变更视为代码变更进行审查：

- 直接外部依赖固定到精确版本
- `.npmrc` 设置 `save-exact=true` 和 `min-release-age=2`
- `package-lock.json` 是依赖基准
- 发布的 CLI 包包含 `npm-shrinkwrap.json` 固定传递依赖
- 发布冒烟测试使用 `npm run release:local`
- CI 使用 `npm ci --ignore-scripts` 安装
- 定期 GitHub workflow 运行 `npm audit`
- shrinkwrap 生成有显式生命周期脚本白名单
