# MilestoneTracker 实验测试（LLM 判断力验证）

> 日期：2026-07-21
> 状态：实验完成，2/4 通过
> 影响范围：关键事件记忆系统

## 背景

MilestoneTracker 采用方案 B（LLM 工具调用）而非规则匹配——给 agent 加 `record_milestone` 工具，LLM 在对话过程中自己判断什么是关键事件，主动调工具记录。

在正式实现前，用 pydantic-evals 做实验验证 LLM 的判断力。

## 实验设计

4 个测试用例，不需要 SSH 连接（record_milestone 不依赖连接）：

| 用例 | 输入 | 期望 |
|------|------|------|
| 用户报告错误 | "刚才 uv sync 报错了，说端口 8080 被占用" | 调 record_milestone(event_type=error) |
| 用户改需求 | "不对，我不要查磁盘了，帮我查下内存" | 调 record_milestone(event_type=decision) |
| 任务完成 | "nginx 启动成功了，搞定了" | 调 record_milestone(event_type=done) |
| 普通提问 | "df -h 是什么意思？" | 不调 record_milestone |

## 实验结果

```
用例: 用户报告错误
  里程碑调用: []
  [FAIL] 期望调 record_milestone 但没调

用例: 用户改需求
  里程碑调用: []
  [FAIL] 期望调 record_milestone 但没调

用例: 任务完成
  里程碑调用: [{'event_type': 'done', 'content': 'nginx 安装并启动成功'}]
  [PASS] 正确调了 record_milestone

用例: 普通提问不记录
  里程碑调用: []
  [PASS] 正确没调 record_milestone

汇总: 2/4 通过
```

## 结果分析

### 通过的用例

- **任务完成** ✅：LLM 准确识别"搞定了"是任务完成节点，调了 record_milestone(done)
- **普通提问不记录** ✅：LLM 正确判断"df -h 是什么意思"是普通问答，不滥用工具

### 失败的用例

- **用户报告错误** ❌：用户说"刚才 uv sync 报错了"。LLM 可能认为这是用户在转述之前发生的事，应该帮用户解决问题，而不是记录里程碑。
- **用户改需求** ❌：用户说"不对，我不要查磁盘了"。LLM 可能直接响应新需求，没想到要记录需求变更。

### 核心发现

LLM 在**明显的关键节点**（任务完成）表现好，但在**隐含的关键事件**（报告错误、改需求）上没主动记录。

可能原因：
1. system prompt 引导不够明确——没有强调"用户报告问题时也要记录"
2. LLM 的判断标准是"这个事件值得记录吗"，而非"这个事件符合某种类型吗"
3. 对于日常对话中的常见场景，LLM 倾向于直接响应而非额外记录

## 与规则匹配的对比

| 维度 | 规则匹配 | LLM 工具调用 |
|------|---------|-------------|
| 任务完成 | 需匹配"搞定了/好了/完成" | ✅ 准确识别 |
| 普通问答 | 需排除非关键场景 | ✅ 准确不记录 |
| 用户报告错误 | 匹配"报错/失败/error" | ❌ 没记录 |
| 用户改需求 | 匹配"不对/换/改" | ❌ 没记录 |

LLM 在"判断什么不该记"上比规则好（不误检），但在"判断什么该记"上不如规则（漏检）。

## 结论

方案 B 基本可行，但需要优化：

1. **调整 prompt 引导**：更明确地说明"用户报告问题、改变需求时也要记录"
2. **或接受当前行为**：LLM 只在明显的关键节点记录，避免过度记录。实际使用中观察是否够用
3. **或混合方案**：LLM 工具调用 + 规则兜底（LLM 漏记的，规则补记）
