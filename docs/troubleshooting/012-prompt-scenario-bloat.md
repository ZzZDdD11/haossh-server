# Prompt 场景枚举堆叠：加了又删的"部署流程"小节

> 日期：2026-07-22
> 状态：已解决（撤回改动）
> 影响范围：system prompt 的可维护性

## 背景

009 号问题记录了"用户已给出仓库 URL，agent 仍反问要部署哪个仓库"。修复时最初的做法是给 `ssh_operator.md` 加两处：
1. 一条通用规则："先提取消息中已给出的信息，再决定要不要问"
2. 一个"代码部署流程"小节：7 步标准部署动作序列（clone → 探测项目类型 → 装依赖 → 找启动方式 → 验证 → 汇报）

第一次验证（两处都加）确认问题修复了。

## 问题

用户指出：这种"场景专属流程小节"的做法**不可持续**——运维场景千变万化（部署、数据库迁移、SSL证书、K8s发布……），照这个思路每遇到一种新场景就要在 prompt 里加一段，prompt 会无限堆叠，越来越长、越来越难维护。

## 根因

混淆了两种性质不同的修复:

| 改动 | 性质 | 是否可持续 |
|---|---|---|
| "先提取已知信息再问" | 通用原则，覆盖所有场景 | 一次写好，永久有效 |
| "代码部署流程"7步 | 场景枚举，只对"部署"有效 | 每种新场景都要加一段，无限堆叠 |

这正是本次会话反复出现的同一条设计原则的反例——008/010/011 号问题都是"用一条通用规则/机制替代场景枚举"（exit code 替代 error 关键词枚举、持久 shell 替代"记得 cd"提示、观测 cwd 替代声明 workspace）。这次一开始加部署流程小节，恰恰是反着做了一次。

## 验证：场景小节到底有没有用

做了对照实验，两种情况下都用同一句真实案例测试（消息里已给出仓库 URL + 端口）：

| 条件 | 结果 |
|---|---|
| 通用规则 + 部署流程小节 | 不反问，正确提取信息 |
| 只有通用规则，删掉部署流程小节 | 不反问，正确提取信息，且模型自己完整规划出等价的部署步骤（系统探测→克隆→分析项目结构→配置端口→验证） |

两种条件下结果完全等价——证明模型作为"10年经验 SRE"人设本身就知道怎么部署代码，场景流程小节是纯冗余，只有通用规则在起作用。

## 解决方案

撤回"代码部署流程"小节，只保留通用规则（"先提取消息中已给出的信息，再决定要不要问"）。

## 效果

对照实验的两次验证均通过（[PASS] 模型没有反问仓库信息），确认删除场景小节不影响修复效果。

## 复盘：为什么会犯这个错误

设计方案时没有先做"这条改动是通用原则还是场景枚举"的自我检查，凭直觉认为"给出具体步骤"更保险。实际上模型的专业知识本身就能覆盖大部分标准操作流程，写场景小节是低估了模型能力、高估了"显式指导"的必要性。

## 后续

现有 prompt 里还有三个类似的场景小节（软件安装流程、故障排查流程、Docker排障流程），是比这次更早的历史遗留，可能同样是冗余的。暂不处理——需要逐个做同样的"加/删对照验证"才能确认，不能因为分类相同就一起删除，留作后续单独的 prompt 精简任务。
